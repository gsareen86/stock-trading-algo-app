# Design: llm-gateway-and-observability

## 1. An explicit chain, not `litellm.Router`

Configuration extends the existing nested pattern rather than inventing a second one:

```
LLM_ROUTE__NARRATIVE=ollama/llama3.1
LLM_FALLBACK__NARRATIVE=anthropic/claude-sonnet-5,openai/gpt-4o
```

A task with no `LLM_FALLBACK__` entry keeps today's behaviour exactly.

The roadmap entry for this increment says "LiteLLM router", and `litellm.Router` does provide
fallbacks — `model_list` of group aliases plus a `fallbacks` map. **It is deliberately not used
here**, for one reason that is decisive given what this increment is for: Router performs
failover *inside* a single `acompletion` call, so the individual attempts are not observable
from outside. This change exists to make every attempt accountable, and
`llm-observability` requires a row for the failed primary *and* a row for the successful
fallback. A black-box failover cannot produce that.

So the gateway walks the chain itself: one `litellm.acompletion` per rung, in order, stopping
at the first success. What Router would have added beyond that is retries (already covered by
`num_retries` per call), cooldowns (already covered by the circuit breaker) and load balancing
across duplicate deployments (not a thing this platform has). The marginal value was low and
the cost — losing per-attempt visibility — was exactly the wrong trade for this change.

The chain is built from settings and pruned before dispatch, so the loop stays small and the
policy lives in one place.

## 2. Breaker and fallbacks have to cooperate

The circuit breaker is per-provider and coarse: after N consecutive rate limits it stops
issuing requests to that provider entirely. Left as-is, it would fight the Router — a task
whose primary provider is breaker-open would return `None` without ever trying its fallback.

So the gateway now resolves the chain *before* dispatching:

1. Build the ordered chain: primary, then each fallback rung.
2. Drop any rung whose provider has an open breaker.
3. If the chain is empty, return `None` without a network call.
4. Otherwise dispatch to the first surviving rung, with the rest as Router fallbacks.

The breaker therefore prunes the chain rather than vetoing the call. That keeps its original
purpose — never waste seconds on a provider known to be rate-limiting — while letting a
healthy provider further down the chain answer.

`num_retries` handles *within-rung* transient failure; the breaker handles *across-call*
memory; the chain handles *cross-provider* failover. Three different timescales, no overlap.

## 3. The result must name the model that actually answered

With fallbacks, "which model produced this?" stops being knowable from configuration. That
matters more here than in most systems: a `Verdict.narrative` is meant to be traceable, and
"generated by the configured model" is not a fact if the configured model was down.

`LLMResult.model` therefore reports the model that *served* the request — determined by which
rung actually answered, not by reading settings — and a new `requested_model` field records
what was asked for. When they differ, a fallback happened, and both the call log and the trace
say so.

Using the rung is deliberately preferred over parsing `response.model`: providers echo
aliases, strip prefixes and occasionally return a different revision than requested, whereas
the gateway dispatched to exactly one known target and knows which one returned.

## 4. The call log

`trading.llm_calls`, one row per attempt, written **regardless of outcome** — including cache
hits, breaker short-circuits and budget refusals. A log that only records successes cannot
answer "why did narratives stop appearing?", which is the question it exists for.

Status is a closed set: `ok`, `cached`, `failed`, `rate_limited`, `breaker_open`,
`budget_exceeded`. Those are distinguishable failure modes with different fixes, and collapsing
them into a boolean would throw away the diagnosis.

Writing the log must never be able to break a call. It is wrapped so a logging failure is
swallowed and warned about — the same rule the gateway already follows for provider failure.
An observability layer that can take down the thing it observes is worse than none.

**Cost is nullable.** LiteLLM reports a computed cost for hosted providers and nothing for
local ones. Recording `0.0` for a local call would be defensible, but it makes `SUM(cost)`
silently mean "cost of the paid subset" while looking like a total. `NULL` forces that
distinction to stay visible, and the usage endpoint reports paid and unpriced call counts
separately.

## 5. The budget guardrail

A daily USD cap (`LLM_DAILY_BUDGET_USD`, unset = unlimited), evaluated against the sum of
recorded cost since the start of the current IST day.

Three properties worth stating, because each is a decision rather than an accident:

- **Local models are exempt.** They cost nothing, so a budget breach must not disable the one
  provider that could still work for free. When the cap is hit, tasks routed to local models
  continue; only paid rungs are refused.
- **It fails soft.** Exceeding the budget returns `None` like any other failure, so callers
  keep their non-LLM path. It is a spending limit, not a kill switch.
- **It is checked before dispatch, not after.** A cap enforced after the fact is not a cap.

The check reads a cached daily total refreshed on write, rather than aggregating on every
call — a `SUM` per LLM request would put the database on the hot path of every narrative.

## 6. Why usage lives in the app, not only in Langfuse

Langfuse is optional and, in the common local-only setup, absent. The predecessor's most
useful observability feature was a plain table the dashboard read. `GET /llm/usage` reports
spend and tokens grouped by day, task and provider from `llm_calls`, so the question "what did
today cost?" is answerable with no external service configured.

Langfuse remains the place for *trace* depth — nested spans, prompt/response payloads. The
local log is the place for *accounting*. They are not redundant; they answer different
questions.
